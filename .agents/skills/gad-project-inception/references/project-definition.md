# Project Definition Method

Use this reference when preparing or revising a Project Definition Proposal.

## Required distinctions

Keep these separate:

- **Confirmed fact**: explicitly supplied by the user or observable in existing project reality.
- **Assumption**: a plausible but unconfirmed interpretation.
- **Open question / deferred decision**: a decision that is not yet known or does not need to be made now.

Never convert an assumption into a project fact merely because it was not rejected.

## Proposal schema

A Project Definition Proposal should cover only what is needed to define the project:

1. **Vision** — concise intended outcome.
2. **Problem statement** — current situation, pain point, affected user/consumer, and why the current workflow is insufficient.
3. **Target users / consumers** — who directly uses or consumes the system outcome.
4. **Goals** — outcomes this project must enable.
5. **Non-goals** — outcomes intentionally excluded from the current project definition.
6. **Scope** — explicit in-scope and out-of-scope boundaries.
7. **Core use cases** — a small set of value-defining scenarios, not an exhaustive feature inventory.
8. **Constraints** — user-confirmed business, technical, operational, legal, cost, time, or compatibility constraints.
9. **Success criteria** — observable indicators that the project is achieving its purpose. Do not design the detailed verification plan here.
10. **Assumptions** — unconfirmed beliefs that may later need validation.
11. **Known risks** — project-level concerns only, not delivery-batch risk scoring.
12. **Open questions / deferred decisions** — matters intentionally unresolved.
13. **Scope challenge** — what was removed, deferred, or challenged as premature.
14. **Recommended next step** — normally G1 approval, revision, or clarification.

## Boundaries

Project inception answers **WHAT** and **WHY**. It does not decide the high-level system architecture, detailed technical stack, batch design, worker topology, or capability allocation.

A user-specified technology may be recorded as a project constraint. A technology inferred by the agent is not a project constraint.
