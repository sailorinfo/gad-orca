# A2 working proposal — first v0.1 slice: no-HEAD Bootstrap

Status: draft for GAD Lead and governance; no execution authorization. Base: `85c3195c2dbd4eb07e8ea0bb5c385484ab94d9f6` on `main`. Project state: `ACTIVE`; no product batch is yet baselined.

## Implementation proposal and requirements draft

**Objective.** From an existing, empty Git clone with no `HEAD`, `gad-project init --start-lead --mode bootstrap` should install the supplied GAD package and skills, establish an auditable root commit containing only installer-owned files, and pass a real `HEAD` to the existing Lead launcher. This is the first independently verifiable part of `PROJECT.md` §7(1), not completion of all installation, Bootstrap, or v0.1 acceptance criteria.

**Scope.** The `init` path of `gad-lead/tools/gad-project.ps1`, its `--commit`/`--start-lead` interaction, bounded error reporting, and focused verification. Preserve safe copy behavior, package/skill validation, existing-HEAD behavior, and the established Orca launch boundary. Commit identity/configuration and Orca/Agent availability are explicit prerequisites with actionable diagnostics. The command and state contracts below are requirements, not an implementation algorithm.

### Command matrix and acceptance contract

`--mode bootstrap` is the only mode approved for live launch in this slice. `init` with no `--start-lead` treats `--mode` as inert. An unsupported mode or option still fails argument validation. `--commit` requests a commit of installed-path changes only; `--start-lead` on no HEAD implies that same root commit even when `--commit` is absent. `--start-lead` on existing HEAD does not imply a commit.

| Initial HEAD | Invocation | Expected observable outcome |
| --- | --- | --- |
| absent | `init` | Install safe-copy manifest only; no commit, no launch. HEAD remains absent. Report `installed=true`, `committed=false`, `leadStarted=false` and next command. |
| absent | `init --commit` | Install; create one root commit of the authorized tree; no launch. |
| absent | `init --start-lead --mode bootstrap` with or without `--commit` | Install; create or reuse the one valid root commit; start/reuse one Bootstrap Lead against that HEAD. Never invoke Orca while HEAD is absent. |
| present | `init` | Install safe-copy manifest; HEAD unchanged; no launch. |
| present | `init --commit` | Commit only installed-path changes if any, preserving unrelated index entries; otherwise report no new commit. Never rewrite or amend existing HEAD. |
| present | `init --start-lead --mode bootstrap` without `--commit` | Install, keep HEAD unchanged. Launch/reuse only if existing HEAD already contains the exact installed manifest; otherwise block with `commitRequired=true` and do not launch from an incomplete base. |
| present | `init --commit --start-lead --mode bootstrap` | Commit installed-path changes if any, then launch against resulting HEAD. |
| either | any of the above plus `--dry-run` | Validate inputs and compute a plan only: no copy, index/HEAD change, commit, or Orca call. Report predicted manifest, needed commit, and launch intent; never report a simulated action as completed. A no-HEAD dry run does not require Git identity because no commit occurs. |

All successful calls return a machine-readable distinction between `HEAD` before/after, created commit versus reused HEAD, installation state, and Lead launch state. For a no-HEAD retry after a successful root commit, the existing-HEAD rows apply; an identical manifest must not create another commit. If a no-HEAD root commit cannot be created, `--start-lead` fails without launching.

### Authorized tree and user-state boundary

For the no-HEAD root commit, define manifest `M` at invocation start as the relative file paths and exact byte hashes recursively supplied by the selected `--package`/resolved `gad-lead` directory and the five validated `gad-core/skills/<name>` directories. Each package file maps to `gad-lead/<relative-path>`; each skill file maps to `.agents/skills/<name>/<relative-path>`. The source enumerator must include hidden files and be deterministic; unsupported link/reparse entries or unreadable files block before any commit. Normalize relative paths and reject duplicates, traversal, or case-insensitive collisions. Include every source file actually copied; do not assume that `MANIFEST.json` alone enumerates the payload. Record `M` as path/SHA-256 pairs in verification evidence. The root commit tree must contain **exactly** `M` at those paths and exactly those bytes, with no other paths, regardless of Git ignore rules; regular files use Git mode `100644`. A differing destination byte or any extra file under the managed destination trees blocks no-HEAD commit; identical destination bytes are reusable. Existing files outside those trees, whether tracked, staged, untracked, or ignored, are never copied, staged, committed, deleted, or overwritten. An existing `.gitignore` or other outside-tree file remains outside the root tree.

The caller's primary Git index is an owned user state: preserve each preexisting entry's path, mode, object ID, stage, and intent-to-add flag both outside **and inside** destination trees on success or failure. A pre-staged destination entry whose worktree bytes match `M` is permitted and must remain staged exactly as before; if its staged blob differs from `M`, block before commit even when worktree bytes match, because a successful root commit would leave a contradictory staged version. Preexisting unmerged entries inside destination trees also block. For existing HEAD `--commit`, preserve preexisting staged entries by isolating the installer commit; reject any preexisting staged destination entry whose blob conflicts with intended installed bytes. Existing destination worktree files differing from the source remain a safe-copy conflict in every mode. Never use a broad staging or unscoped commit that absorbs the caller's index. After a successful commit, installed paths match the committed bytes; all unrelated worktree bytes and index entries remain byte-for-byte/state-for-state unchanged. A preexisting tracked path in a no-HEAD clone is impossible because HEAD is absent, but staged paths can exist and are covered here.

**Non-scope.** `new`, general existing-repository upgrades, automatic adoption or G1/G2 approval, `PROJECT_STATUS.md`, `gad-*` skill changes, Lead recovery/dispatch, release packaging, cross-platform support, or an end-to-end CLOSED demonstration. Do not amend existing history or invent a formal baseline. Do not silently convert `--commit` into permission to commit arbitrary staged files.

**Current state and evidence.** `gad-project.ps1` checks `HEAD` via `git rev-parse --verify HEAD` (lines 315–325). `init` validates a Git worktree and installs files (481–502). It commits only when `--commit` is present (506–539), then `--start-lead` rejects no-HEAD repositories (545–548). `new --start-lead` explicitly requires `--commit` (470–473); `init` has no equivalent recovery. The current `git add -- .agents/skills gad-lead` limits staging to installed trees, but `git commit` without a path commits *all* pre-staged changes; this violates the narrow-root-commit requirement. `Copy-FileSafe` already skips byte-identical files and blocks differing files (210–233). The launcher obtains `HEAD` and hands its commit to Orca worktree creation (`gad-lead.ps1` 1692–1718). No relevant tests or RESULT evidence were found in the repository. Inspection is static: no installer or Orca workflow was executed in this A2 role.

**Architecture fit and reuse.** The installation/Bootstrap module owns Git setup and package copy; Orca remains sole worktree/terminal/Agent orchestrator. Reuse `Assert-GitProject`, `Test-GitHasHead`, `Copy-TreeSafe`, and the existing `gad-lead start --mode bootstrap` handoff. The installer should establish an auditable root commit before invoking the launcher, preserve user index contents, and verify the resulting `HEAD`. A minimal, path-scoped Git operation is preferable to a second bootstrap service or state database. No architecture-baseline change is proposed. The existing `gad-core` skill source and package are inputs, not new runtime dependencies.

**Capability allocation.** PowerShell Program logic handles preconditions, safe copy, Git path isolation, commit and retry diagnostics. Git is the existing Tool for repository state. Orca/Lead remains the existing external execution boundary. No new MCP, Skill, Agent, dependency, or orchestration component is needed for the feature. Implementation should be one bounded worker; independent review follows under the applicable profile. Parallel code editing would overlap one script and add integration risk.

**Alternatives and over-design test.** A manual root commit leaves the promised empty-clone Bootstrap unfulfilled. A blanket `git add -A` or unscoped `git commit` risks including user material. A temporary branch or second project-state store adds complexity without satisfying a current need. The smallest design is a narrowly scoped root-commit path plus explicit failure diagnostics. If Git cannot preserve unrelated index entries reliably with that design, implementation must stop and request renewed readiness instead of widening commit authority.

**Impact and risk.** Product behavior: affected for no-HEAD `init --start-lead` and the existing-HEAD `--commit`/launch safety guard. Git history/index: affected, with potential disclosure or integrity consequences if unrelated staged files enter a commit. `new` behavior: regression risk only, to be checked. Orca: existing boundary only. No schema or data migration. Root commits are persistent; the tool must not use destructive reset/clean/force. No credentials or source file contents should be printed in diagnostics.

### Failure and retry postconditions

Every failure reports phase (`validate`, `copy`, `stage`, `commit`, `launch`), `headBefore`, `headAfter`, `rootCommitCreated`, copied/reused/conflicting relative paths, `indexPreserved`, `leadLaunchAttempted`, `leadStarted`, and a safe next action; JSON mode must emit one parseable object even on failure. Do not expose file contents or secrets. A source/manifest/index conflict detected before copying leaves HEAD, primary index, and worktree unchanged. Copy failure may leave a subset of byte-identical installed files; report that subset, leave HEAD absent and primary index unchanged, and permit retry after cause repair. Stage/isolation failure leaves copied files but no HEAD, no primary-index changes, and no Orca call. Commit failure (for example missing identity) leaves copied files, no HEAD, unchanged primary index, no Orca call, and no false success flag; retry uses the same manifest and does not duplicate or overwrite files. Successful root commit followed by launch failure leaves that exact HEAD/tree and caller index/worktree intact, reports launch error and `rootCommitCreated=true`, and retries through existing-HEAD behavior without another root commit. Any unexpected partial HEAD/tree or altered caller index is a stop condition, not an automatic cleanup opportunity. For an existing-HEAD invocation, stage/commit failure leaves prior HEAD and index unchanged; an already completed installed-path commit is never rolled back because a later launch fails.

**Stop conditions.** Cannot establish a root commit without committing unrelated index entries; source package conflict; commit identity unavailable; Orca/Agent unavailable for live launch; changed public CLI contract or dependency; any need to modify approved architecture/rules/status/skills; inability to guarantee the failure postconditions above. Report the observed state and route material deviation through governance. There is no approval in this proposal.

## Verification-plan draft

Use disposable no-HEAD and existing-HEAD repositories created only by an authorized implementer/verifier after G3. Run every command-matrix row, with and without `--commit` where specified, and dry-run on both HEAD states. Record commands, exit codes/JSON diagnostics, HEAD before/after, `git status --porcelain=v2`, raw index entries (`git ls-files --stage` plus intent-to-add), root commit tree (`git ls-tree -r`), and `git log -1 --format=%P` (empty parent list). Compare every tree path, mode and blob byte hash to `M`; verify no extra path enters the tree. Include pre-staged entries outside and inside the destinations (identical blob, conflicting blob, unmerged), unrelated untracked and ignored files, extra managed-directory file, identical prior install, and differing target file. Snapshot caller index bytes and worktree hashes before/after every success/failure case. Exercise copy, stage/isolation, commit-identity, and Lead-launch failures; check each phase-specific postcondition and same-manifest retry. Exercise existing-HEAD `--commit` index isolation and `--start-lead` incomplete-base guard; check `new` behavior for regression only. For live Orca proof, verify exactly one Lead worktree/terminal is created or reused and its Git base equals the valid root commit; capture launcher output/lineage without treating it as Gate approval. A dry run cannot prove the real commit or launch path.
